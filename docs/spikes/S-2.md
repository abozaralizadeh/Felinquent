# S-2: cost of window polling

Run on 2 Nov 2026, Apple Silicon Mac, release build, `cargo run --release --bin probe`.

The probe calls `CGWindowListCopyWindowInfo` (on-screen windows, no desktop elements) and filters to normal app windows.

| Read | Time |
|---|---|
| Window list, steady state | about 1.6 ms |
| Mic in use (CoreAudio) | about 1.5 ms |
| Camera in use (CoreMediaIO) | about 0.02 ms |
| Idle seconds and since-key seconds | under 0.1 ms |
| First read after start | much slower, roughly 150 ms (worked out from a 16 ms average over 12 reads, not timed on its own) |

At 4 Hz the window list alone is about 6 ms of work per second. That is well inside the 0.5 percent CPU budget. The mic check does not need 4 Hz, so poll it at 1 Hz.

## What the real list looks like

The raw list is noisy. A usual desktop gave six entries, among them:

- Browser toolbar slivers, 81 to 158 points tall, full width.
- Windows on a second display, with negative `y` (Universal Control).
- Real windows, like a 1440x778 browser page.

The overlay keeps only windows at least 100 points tall that overlap the screen and do not start above it. Titles are not read, so no Screen Recording permission is needed.

## Not measured

- Whole-process CPU of the running overlay over time (no Activity Monitor run yet).
- Occlusion-aware platforms on real windows, beyond the unit tests.

Result: **works, cost is small**. The CPU number for the whole app still needs a proper soak test (P1).
